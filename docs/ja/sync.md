# 同期システム

同期システムは、FE Search AI が使う検索インデックスを構築・維持します。

## 同期で行われること

同期では、選択したWordPressの投稿・固定ページ・カスタム投稿タイプからコンテンツを抽出します。各投稿について以下を実行します。

1. コンテンツをチャンクに分割（デフォルト約1,000文字。`fe_search_ai_chunk_size` で調整可）。
2. 任意でチャンクごとの構造化サマリー（トピック・事実・エンティティ・キーワード）をチャットプロバイダーで生成。
3. 選択したベクトル化 AI でベクトルを生成し、Qdrantに保存。
4. `{prefix}fe_search_ai_keyword_index` テーブルにBM25ランキング用のキーワードインデックスを構築。

## 同期モード

### 「変更を同期」（スマート同期）

前回完了した同期以降に変更されたコンテンツのみを処理します。具体的には:

- 公開状態でなくなった投稿のインデックス行を削除します。
- `post_modified_gmt` が前回同期タイムスタンプより新しい投稿をインデックスします。
- 前回同期以降に同期設定が変わっている場合は実行を拒否し、「インデックスを再構築」の実行を促します。

スマート同期には基準（前回同期タイムスタンプ）が必要です。一度も同期が完了していない場合は、先に「インデックスを再構築」を1回実行するよう案内されます。

### 「インデックスを再構築」（全同期）

`{prefix}fe_search_ai_vectors` と `{prefix}fe_search_ai_keyword_index` を空にしてから、対象となる全投稿を一からインデックスし直します。次のタイミングで使います。

- 初回セットアップ時
- 同期対象、トークナイザー、ベクトル化 AI などインデックスに影響する設定を変更した後
- インデックス健全性の指標に異常がある場合（後述）

### リアルタイム同期

有効化された投稿タイプの投稿が公開・更新されると、`save_post` で再インデックス用のキューに追加されます。既存のインデックス行は保存時にすぐ削除されますが、実際のインデックス処理（チャンク分割、任意のサマリー生成、ベクトル化 API 呼び出し、インデックス書き込み）は WP-Cron（`fe_search_ai_process_sync_queue`）経由でバックグラウンド実行されるため、外部 API 呼び出しによって保存処理が遅くなることはありません。投稿のゴミ箱移動・削除（`wp_trash_post`、`delete_post`）ではキューとインデックスから同期的に削除されます。

`publish` ステータスのみが対象で、自動保存とリビジョンはスキップされます。キューされたジョブの実行時にもステータスと設定が再検証されます。投稿の言語は Polylang、WPML、Bogo があればそこから検出し、なければサイトロケールにフォールバックします（`fe_search_ai_post_language_code` フィルター）。

関連フィルター: `fe_search_ai_realtime_sync_background`（`false` を返すと保存リクエスト内で同期的にインデックス）、`fe_search_ai_sync_queue_time_limit`（キュー実行1回あたりの最大秒数、デフォルト `50`）。

全同期とリアルタイム同期のタイムスタンプは別々に記録され、「最終一括同期」と「最終リアルタイム同期」として表示されます。

## インデックス健全性の指標

「同期」タブにはインデックスの状態が表示されます。

| 指標                           | 意味                                                                                                            |
| ------------------------------ | --------------------------------------------------------------------------------------------------------------- |
| **同期済みの記事**             | インデックスに存在するユニークな投稿数。                                                                        |
| **ベクトル数**                 | `{prefix}fe_search_ai_vectors` のチャンク行数。1投稿は通常複数チャンクになります。                              |
| **キーワードトークン数未設定** | `keyword_token_count` が `0` のチャンク行数。非ゼロならそのチャンクではBM25キーワードマッチが機能していません。 |
| **平均キーワードトークン数**   | チャンクあたりの平均トークン数（0の行を除く）。ゼロに近い場合はトークナイズが機能していない可能性があります。   |
| **キーワードインデックス行数** | `{prefix}fe_search_ai_keyword_index` の総行数（term頻度）。                                                     |

**キーワードトークン数未設定** が非ゼロなのに **キーワードインデックス行数** に行がある、またはキーワード検索結果にBM25スコアが付かない場合は、「インデックスを再構築」を実行してメタデータを再構築してください。

## バッチ処理と中断

同期はAJAXバッチ（1リクエストあたり「バッチサイズ」件）の逐次処理で、プログレスバーが表示されます。最終同期タイムスタンプと同期設定ハッシュは**全バッチ完了後**にのみ更新されます。

同期が中断した場合（ブラウザを閉じた、タイムアウト、サーバーエラー）:

- 「インデックスを再構築」は開始時にインデックスを空にするため、もう一度「インデックスを再構築」を実行する必要があります。「変更を同期」を再実行しても前回完了した同期以降に変更された投稿しか処理されず、インデックスは不完全なままです。
- 中断した「変更を同期」はそのまま再実行できます。処理済みの投稿は既にインデックスされており、再処理しても問題ありません（投稿単位で冪等。再インデックス前に既存行は削除されます）。

同期が繰り返し止まる場合は「バッチサイズ」を下げ、PHP の `memory_limit` / `max_execution_time` を確認してください。

## 検索トレース（Retrieval Trace）

すべてのチャットリクエストで _検索トレース_（どのチャンクがどのスコアで取得されたかのコンパクトな記録）が生成されます。検索品質の分析に使われ、質問・回答の本文は一切含まれません。

トレースの内容:

- `trace_id`、`sequence_id` — 識別子
- `query_hash`、`query_length` — 質問のSHA-256と文字数（本文そのものではない）
- `pipeline` — どのステージが寄与したか: `bm25`、`qdrant`、`hybrid`、`cohere`
- `metadata.source_counts` — 最終結果が `qdrant`、`keyword`、`both`、`unknown` のどのソース由来かの内訳
- `items` — チャンクごとの `final_rank`、`post_id`、タイトル、チャンク/パーマリンクハッシュ、スコア（`bm25_score`、`qdrant_score`、`hybrid_score`、`cohere_relevance_score`）とランク（`bm25_rank`、`qdrant_rank`、`hybrid_rank`、`cohere_rank`）

### トレースの確認方法

- 「デバッグモード」を有効にすると、`{prefix}fe_search_ai_system_logs` に `Retrieval trace scores captured.` というエントリで検索トレースが記録されます。
- 「検索トレースの永続化」（「詳細設定」タブ）を有効にすると、`{prefix}fe_search_ai_retrieval_traces` と `{prefix}fe_search_ai_retrieval_trace_items` に保存されます。設定した保持期間（デフォルト30日）を過ぎた分は日次ローテーションで削除され、「検索トレースの削除」で一括削除、「アンインストール時にデータを削除」の設定にも従います。

簡易ヘルスチェック: 最終トレースアイテムに `bm25_score` が無いのにキーワードインデックスに行がある場合、チャンクのトークン数がゼロになっている可能性が高いので「インデックスを再構築」を実行してください。

関連フィルター: `fe_search_ai_retrieval_trace_payload`、`fe_search_ai_enable_retrieval_trace_persistence`、`fe_search_ai_retrieval_trace_retention_days`。

## 日本語コンテンツ

日本語サイトではトークナイズがBM25キーワードマッチングに影響します。TinySegmenter（PHP 8.0以上）は外部API不要で使えます。より高精度なトークナイズが必要な場合は Yahoo! JAPAN 日本語形態素解析API を設定できます。トークナイザーを変更した場合は「インデックスを再構築」が必要です。

## 同期のトラブルシューティング

- APIキーが有効か確認（「プロバイダー」タブの「テスト」ボタン）。
- Qdrantのエンドポイント、APIキー、コレクション、およびコレクションのベクトルサイズがベクトル化モデルと一致しているか確認。
- 低スペックのホスティングでは「バッチサイズ」を下げる。
- PHP の memory limit と max execution time を確認。
- 「デバッグモード」を有効にして `{prefix}fe_search_ai_system_logs` を確認するか、`wp-content/debug.log` をチェック。
